## 1. Architectural Review

### Is the broker submission boundary now architecturally impossible to bypass?

**Mostly, not entirely.** Within the three call-site families ES-0001 was scoped to — `BatchConfirmModal.submitAll`'s simple-close path, its OTOCO-roll path, and `SetStopLossButton`'s OCO/restore-fallback/plain-stop paths — the boundary is real, not just tested-in-isolation. A direct grep of `app/portfolio/page.tsx` for every `ttPost(`, `ttPostComplex(`, and `ttValidateOrder(` call site confirms each one of these six live-order calls is written as the callback argument to a `submitCloseOrderIfSafe(...)` invocation (lines 4826–4943, 7665, 7696, 7734). There is no code path today by which one of these six calls can execute without `guardAgainstAmbiguousStructure` and `runLiveCloseOrderSafetyGate` having already returned a pass. This is a structural property, not a convention the next engineer has to remember to follow — an engineer would have to actively move a `ttPost` call out of a callback to break it, not just forget a check.

**It is not universal, though.** The same grep turned up a seventh live-order path outside this boundary entirely: `replacePendingOrder` (`app/portfolio/page.tsx:10651–10683`, wired to the Pending Orders card's `onReplace` prop at line 10958). It reprices an already-placed GTC/stop order by cancelling the existing complex order and resubmitting the same legs and price-effect (read straight from the broker-sourced `PendingOrder`, via `buildReplaceOrder`) at a caller-supplied `newPrice`. This call never touches `analyzePositionStructure`, `runLiveCloseOrderSafetyGate`, or `submitCloseOrderIfSafe` — there is no tick validation, no quote check, no display-vs-payload cross-check, nothing. It predates ES-0001 and was never in scope for either implementation round, so its existence isn't a regression this ticket introduced, but it means the true answer to "is the boundary impossible to bypass" is "impossible to bypass for the paths this ticket touched; a pre-existing, adjacent live-order path was never brought inside it." See Technical Debt Register, TD-1.

### Does any duplicate logic still exist?

No meaningful duplication inside the new module. `closeOrderSafety.ts` and `closeOrderSubmission.ts` each have one clear job and don't restate each other's logic — `closeOrderSubmission.ts` is intentionally thin (108 lines) and delegates all economics to the gate. The one duplication worth naming is conceptual, not textual: `calculateSpreadCredit` (`app/portfolio/page.tsx:1930–1939`, the pre-existing, still-`Math.max(0,…)`-flooring helper) remains in the file, unused by any of the corrected call sites, sitting next to `buildCanonicalCloseIdentity`, which reimplements the same "sum signed leg prices" math correctly. Nothing calls the old function anymore (confirmed by the corrective-round investigation), so it isn't a live defect, but a future reader grepping for "spread credit" will find two implementations of the same idea, one of which is known-wrong. Worth deleting once nothing references it, rather than leaving it as an attractive nuisance for a future edit to accidentally call again.

### Should any helper functions eventually be renamed?

Two candidates, neither urgent. `strategyLabelForStructure` and `structureAnalysisToBlockingIssue` are both accurately named and fine. `isTickValid` (module-internal) is really "is this a whole number of cents" — accurate today given the module's own disclaimer that it isn't the real TastyTrade tick schedule, but if a real tiered tick table is ever wired in, the function should be renamed to something like `isCentDenominated` at that time so its narrower meaning doesn't get inherited by mistake. Not worth a rename on its own.

### Could any APIs be simplified?

The two-guard shape (`guardAgainstAmbiguousStructure` then `guardWithSafetyGate`, both wrapped by `submitCloseOrderIfSafe`) is more ceremony than a single combined guard would need, but the split is deliberate and earns its keep: a null/ambiguous identity genuinely can't be turned into a `LiveCloseOrderSafetyInput` at all (there's no `CanonicalCloseIdentity` to put in it), so collapsing the two checks into one function would just move an internal `if` rather than remove one. Leave it split.

The one real simplification opportunity is in the points/dollars discipline itself: right now, "never multiply by `contractMultiplier` twice" is enforced by naming convention (`entryPricePointsPerUnit` vs. `entryTotalCashFlowDollars`) plus test coverage, not by the type system. A `Points` / `Dollars` branded numeric type (`type Points = number & { readonly __unit: 'points' }`) would make the exact defect this ticket fixed a compile error instead of a naming-discipline-plus-tests defense. This is a real simplification, but it touches every call site that currently passes a bare `number` for these fields (`app/portfolio/page.tsx`'s `enrich()`, `TakeProfitScale`, `SetStopLossButton`, both test files), so it's sized as its own follow-on, not a drive-by. See Technical Debt Register, TD-3.

### Do any safety rules overlap unnecessarily?

Two pairs are adjacent but not redundant, worth naming so a future maintainer doesn't try to "clean up" what looks like overlap:

`PAYLOAD_QUANTITY_MISMATCH` and `LEG_RATIO_MISMATCH` both fire together on the same bad input (a payload leg quantity that doesn't match the plan) — this is intentional, not a bug: `PAYLOAD_QUANTITY_MISMATCH` is the per-leg check ("this specific leg's quantity is wrong"), `LEG_RATIO_MISMATCH` is the whole-payload check ("nothing in this payload scales 1:1 with the requested quantity"). They report the same fixture from two angles on purpose, and the test suite explicitly tests them firing together (`closeOrderSafety.test.ts`, "PAYLOAD_QUANTITY_MISMATCH and LEG_RATIO_MISMATCH block together"). Don't collapse them — a future structure with a non-1:1 leg ratio (none exists today, but the module's own comments anticipate one) would need them to diverge.

`BREAK_EVEN_PNL_MISMATCH` and `DISPLAY_PAYLOAD_ECONOMICS_MISMATCH` can also both fire on the same lying-about-break-even submission. Also intentional: one is intent-specific (only runs when `pricingIntent === 'BREAK_EVEN'`), the other is unconditional (always checks displayed P/L against the plan regardless of intent). Keep both.

### Should any code be extracted into a future shared module?

The points/dollars branded-type idea above (TD-3) is the most valuable future extraction — it would naturally live in a small `lib/portfolio/units.ts` (or similar) shared by any future execution feature that touches broker prices, not just close orders. Beyond that, `deriveMarketablePricePoints`'s debit→ask/credit→bid convention is currently private to this module but restates a rule that also lives, informally, in `app/portfolio/page.tsx`'s `fetchCloseQuote` documentation. If a second execution feature (e.g. a future opening-order safety gate) needs the same convention, it's worth promoting to a small shared `lib/portfolio/marketablePrice.ts` at that point rather than copy-pasting the comment a second time. Not worth extracting speculatively today with only one caller.

### Is the current architecture appropriate for future execution-related features?

Yes, with one caveat. The separation of concerns — deterministic structure analysis, an identity builder that blocks rather than estimates, an immutable plan, an all-block gate, and a thin broker-boundary wrapper whose only job is "don't let the callback run unless both guards passed" — is a good template for the next live-order feature (e.g. opening a new spread, or PT-0002's live/paper mode boundary). The caveat is TD-1: this architecture is only as strong as its adoption. `replacePendingOrder`'s existence proves that a good boundary can coexist with an unguarded seventh door in the same file. Before this pattern is trusted as "the way live orders work in this app," it's worth an explicit inventory of every `ttPost`/`ttPostComplex`/`ttValidateOrder`/`ttDelete` call site in the codebase (not just the ones a given ticket happened to touch) and a decision, per call site, about whether it needs to route through this gate or is genuinely out of scope (e.g. `cancelPendingOrder`, which only deletes and never resubmits economics, is plausibly fine as-is).

## 3. Test Coverage Assessment

Both test files were re-run against the merged code on `main` today and pass exactly as claimed at merge time: `closeOrderSafety.test.ts` — 46/46; `closeOrderSubmission.test.ts` — 19/19.

**Strengths.** The suite's defining habit — asserting literal expected numbers (`0.60`, `120`, `-150`, `30`) instead of re-deriving the expected value with the same formula under test — is exactly right for this domain and should be the house style for any future money-math module. The ambiguity fixtures (two independent same-quantity spreads, 3-short/3-long, naked-vs-naked) cover the actual failure shape the ticket investigates, not just abstract cases. The broker-boundary suite's use of a real `vi.fn()` mock standing in for `ttPost`/`ttPostComplex`, asserted `not.toHaveBeenCalled()` on every blocking path, is doing real work — it's proof, not just an assertion by inspection, which matters a lot for exactly the property (broker call unreachable without both guards passing) that round 1's corrective diff got wrong despite its own tests passing.

**Redundancy.** Some overlap exists between the two files by design, not accident: `closeOrderSafety.test.ts` tests `runLiveCloseOrderSafetyGate` directly (e.g. `PAYLOAD_LIMIT_PRICE_MISMATCH`, `ENTRY_DEBIT_POSITIONS_UNSUPPORTED_LIVE`), and `closeOrderSubmission.test.ts` re-exercises the same rule IDs through `submitCloseOrderIfSafe` (e.g. "does not call the broker when the actual broker limit price... is 100x the plan's"). This isn't wasted coverage — the first file proves the gate returns the right `SafetyCheckIssue`; the second proves that issue actually prevents the broker mock from firing, which is a materially different claim. Worth keeping both, but if this suite grows further, new rule IDs should default to one dedicated gate-level test plus reuse of an existing broker-boundary parametrized case, rather than a fresh full boundary test per rule, to keep the ratio from growing unboundedly.

**Missing edge cases.** A few gaps worth naming, none urgent: (1) no test exercises a structure with more than 4 legs (e.g. a double calendar or a genuinely unsupported multi-expiration combination) — `analyzePositionStructure` operates per symbol+expiration bucket upstream, so this may be entirely out of scope, but that assumption itself isn't asserted anywhere in the test file. (2) No test covers `contractMultiplier` values other than 100 or the invalid case — every options contract in this app is presumably always 100-multiplier, but if that's a hard invariant it's worth one comment or test saying so rather than leaving the parameter looking more general than it's ever actually used. (3) `MATERIAL_PNL_DEVIATION`'s exact threshold boundary (30% exactly) isn't tested at the boundary itself, only comfortably inside and outside it — a boundary-value test (`pctFromMarketable === threshold` exactly) is cheap and would remove any ambiguity about whether the comparison is `>` or `>=` if that ever needs to change.

**Brittleness.** Low. The literal-value style is the opposite of brittle by design — it will fail loudly and specifically if the math changes, which is the intended behavior for a regression suite guarding a financial-loss defect. The one place with any fragility is the two `validInput()`/`validGateInput()` fixture-builder helpers (one per file) — they're not shared, so a future change to `LiveCloseOrderSafetyInput`'s shape needs to be made in two places. Given both files already import from `closeOrderSafety.ts` directly, a shared test-fixture helper module (e.g. `lib/portfolio/__tests__/fixtures.ts`) would remove that duplication. Small, not urgent.

**Fixture setup.** Both files' `leg()` helper and per-describe `creditIdentity()`/`buildValidCreditIdentity()` functions are clear and appropriately minimal. No simplification needed there.

## 5. Sprint Retrospective

**What went well.** The corrective-round pattern itself worked exactly as designed: two consecutive rejections (quantity-as-identity/warn-severity in round 1; the 100x unit defect and unenforced boundary in round 1-corrective) were each caught by Product Owner review before merge, not after, and each round's fix was verified with literal-value tests specifically shaped to catch a recurrence of the exact defect just found — not just "does the math work" but "does this specific wrong number happen again." The broker-boundary extraction (`closeOrderSubmission.ts`) turned an inspection-only claim ("the guard runs before the broker call") into a machine-checked one (a mock that asserts it was never called), which is exactly the right response to round 1-corrective's failure mode of a true claim that turned out not to be structurally enforced.

**What should have been done differently.** The 100x defect and the unenforced-boundary defect were both introduced in the same corrective round that was meant to fix round 1's rejection — meaning the fix for one rejection shipped two new, more severe defects (a live financial-math bug and a false safety claim) rather than zero. Both were caught before merge, which the process is designed for, but a narrower corrective round — fixing exactly what round 1 was rejected for, with a follow-up round for any new capability (typed pricing intent, marketable-price derivation) — would likely have surfaced the unit defect sooner, since the diff under review would have been smaller and the points/dollars renaming wouldn't have been mixed in with several other simultaneous changes. Scope discipline within a corrective round, not just across sprints, is the lesson.

**Lessons learned.** Naming-convention-based safety (distinct field names for points vs. dollars) caught this specific defect only because tests were written to assert literal numbers; a self-consistent-re-derivation test style would have passed the exact same 100x bug silently, since the defect was consistent with itself, just wrong. That's a durable lesson for any future money-math work in this codebase, independent of this ticket. Separately: "the guard function is called" and "the guard function's result is what gates the broker call" are different claims, and the gap between them is exactly where round 1-corrective's boundary claim broke down — worth an explicit review checklist item for any future execution-safety ticket ("show me the broker call is lexically inside the guard's success branch," not "show me the guard is called somewhere in this function").

**Recommendations for future execution-safety work.** Adopt the branded-type approach (TD-3) before the next money-math feature, rather than after a second unit-conflation defect. Do the call-site inventory (TD-1's caveat) before claiming any future gate is "the" boundary for live orders in this app — `replacePendingOrder` shows that a good gate and an ungated door can coexist in the same file without either implementation team noticing, since nobody was looking at the file as a whole from the "every live order must pass through X" angle.

## Round 2 corrective changes (WITHDRAWING round-1-corrective's claims)

The Product Owner's round 2 ruling: *"The ambiguity-analysis correction is directionally accepted, but the submitted diff introduces a critical 100x price-unit defect and does not actually place the tested broker-boundary wrapper on the production submission path."*

This section explicitly withdraws three claims made by round 1's corrective documentation:

1. ~~"`entryPricePerUnit`/`closePricePerUnit` (implicitly dollars) are the correct broker-submittable price fields."~~ **Withdrawn -- this was the critical defect.** `buildCanonicalCloseIdentity` computed `entryPricePerUnit = |netPerShare| * contractMultiplier` (DOLLARS, e.g. 60 for a $0.60 credit), and this value was then fed straight back into `closePricePerUnit` -- which `buildClosePlan` treats as broker option-price POINTS and multiplies by `contractMultiplier` a SECOND time. Every default price computed anywhere from `pos.identity.entryPricePerUnit` (Take Profit, GTC, Cut Losses, Close/Roll defaults, and Snap to Break Even) would have submitted a broker limit price 100x too large. **Fixed**: every field is now explicitly named for its unit -- `entryPricePointsPerUnit`/`closePricePointsPerUnit` (points, e.g. 0.60) versus `entryTotalCashFlowDollars`/`closeTotalCashFlowDollars`/`expectedRealizedPnlDollars` (dollars) -- and `contractMultiplier` is applied exactly once per points-to-dollars conversion, never twice. See the module doc header in `lib/portfolio/closeOrderSafety.ts` and the literal-value regression tests in its test file (an entry of short@1.05/long@0.45 must produce `entryPricePointsPerUnit === 0.60`, not `60`, and a 2-contract break-even close must realize exactly `$0.00`, not `$-11940`).
2. ~~"`submitCloseOrderIfSafe` is the production broker boundary."~~ **Withdrawn -- it was imported and called, but the actual `ttPost`/`ttPostComplex` call remained a SEPARATE statement afterward,** meaning nothing structurally prevented the broker call from being reached independent of the guard's result (only the fact that no bug happened to skip the guard call). **Fixed**: `app/portfolio/page.tsx`'s three live submission paths (`BatchConfirmModal.submitAll`'s simple-close path, its OTOCO-roll path, and `SetStopLossButton.submit`'s OCO/restore-fallback/plain-stop paths) now write their literal `ttPost`/`ttPostComplex`/`ttValidateOrder` call INSIDE the `submitToBroker` callback passed to `submitCloseOrderIfSafe` -- there is no broker-reaching statement in any of these functions outside of that callback. `lib/portfolio/__tests__/closeOrderSubmission.test.ts` proves this with a broker mock for every required scenario.
3. ~~"Quote/payload/break-even checks cannot be bypassed."~~ **Withdrawn for round 1.** `SafetyGateInput`'s `quote`/`actualOrderLegs`/`displayedExpectedPnl` were all optional (`?:`) fields, so an `undefined` value (an omitted key, or a caller bypassing the type) silently skipped validation instead of blocking. **Fixed**: `LiveCloseOrderSafetyInput` makes `quote` (may still be explicitly `null`, but the key itself is required), `actualOrder`, and `displayedExpectedPnlDollars` all REQUIRED fields, and the gate's runtime check uses `input.quote == null` (catching both `null` and `undefined`) rather than a truthiness check that could silently no-op on an unexpected `undefined`.
4. ~~"Debit-opened positions are supported end-to-end."~~ **Corrected, not merely re-asserted.** Round 1's pure `buildCanonicalCloseIdentity`/`computeBreakEvenClose` functions correctly compute debit-entry economics (this was true and remains true, proven by literal-value tests both directions), but `app/portfolio/page.tsx`'s SURROUNDING default-price/GTC/stop computations were, and remain, hardcoded to assume credit-at-entry -- they were never actually wired to derive a Credit close for a debit-opened position. Claiming "both directions are supported" because the pure function test passed, while the production UI hardcodes `requestedClosePriceEffect: 'Debit'` everywhere, would have been the exact overclaim the Product Owner warned against. **Fixed honestly, per the Product Owner's explicit instruction to hard-block rather than overclaim**: `runLiveCloseOrderSafetyGate` now hard-blocks any debit-opened position's LIVE submission with `ENTRY_DEBIT_POSITIONS_UNSUPPORTED_LIVE`, before any quote/payload/price validation even runs. The pure identity/plan/break-even functions remain correctly bidirectional (and tested both ways) for whenever this production limitation is later lifted.

### New in round 2: typed pricing intent, marketable-price derivation, actual-price/effect cross-checks

- **`PricingIntent`** (`'CUSTOM' | 'MARKETABLE' | 'BREAK_EVEN' | 'PROFIT_TARGET' | 'STOP_LOSS' | 'ROLL'`) is now threaded from the UI action that triggers a submission (Take Profit -> `MARKETABLE`/`PROFIT_TARGET`, PLACE_GTC -> `PROFIT_TARGET`, Cut Losses -> `STOP_LOSS`, Close/Roll -> `ROLL`, SetStopLossButton -> `STOP_LOSS`) through `ClosePlan.pricingIntent` and into the gate. When `pricingIntent === 'BREAK_EVEN'`, the gate validates the ACTUAL plan being submitted -- its `closePricePointsPerUnit` and `requestedClosePriceEffect` must equal the identity's own computed break-even values (within a one-cent tick tolerance), and `expectedRealizedPnlDollars` must be ~$0 -- rather than round 1's behavior of always silently building a SEPARATE theoretical break-even plan as a pure self-consistency check disconnected from what the operator actually declared they were doing. A submission that claims `BREAK_EVEN` but whose actual price is a disguised profit-target is now hard-blocked (`BREAK_EVEN_PNL_MISMATCH`), not silently passed because the self-check plan happened to be internally consistent.
- **Marketable price is now derived inside the gate from required quote evidence**, not an optional caller-supplied `liveClosePricePerUnit`. Per the Product Owner's explicit instruction and matching `app/portfolio/page.tsx`'s own pre-existing `fetchCloseQuote` convention (`netAsk` = short legs @ ask / long legs @ bid = "marketable now, fills fast"; `netBid` = the patient/best-price side): a Debit close's marketable reference is `netAsk`; a Credit close's is `netBid`. `MATERIAL_PNL_DEVIATION` now runs unconditionally for every live plan using this derived value.
- **`ActualBrokerOrderEvidence`** (required on every live gate input) now carries the actual broker limit price (points) and price effect, not just legs/quantities. New rules `PAYLOAD_LIMIT_PRICE_MISMATCH` and `PAYLOAD_PRICE_EFFECT_MISMATCH` hard-block if the real broker payload's price or effect ever diverges from the plan -- this is the exact cross-check that would have caught the 100x defect at the boundary even if the unit bug had somehow slipped past the plan-construction layer itself.

### `SetStopLossButton` now acquires quote evidence before submission (round 2 correction #4)

Round 1 passed no `quote` field at all to the gate for `SetStopLossButton`'s submission (an omission the round-1 optional-field design allowed to silently skip quote validation). `SetStopLossButton.submit()` now calls the same `fetchCloseQuote` BatchConfirmModal uses immediately before running the gate, so a missing/one-sided/crossed quote hard-blocks a stop-loss/OCO submission exactly as it does for every other close action -- there is no quote-evidence exception for this dialog.

## Problem

A real, live "Snap to Break Even" close-order action on the Portfolio page resulted in an actual financial loss. The approved investigation hypothesis was that this was caused by position grouping too broad to distinguish economically distinct spreads (symbol + expiration only, no strike/direction/quantity discriminator), letting two independently-opened spreads merge into one displayed `Position`, with break-even computed from the merged group's aggregate economics rather than either spread's true economics.

## Investigation — confirmed root cause

This section is unchanged from the first round and remains accepted by the Product Owner. Read directly (not delegated) against `app/portfolio/page.tsx` as it existed on `main` before this ticket:

1. **Grouping key was too broad.** `loadPositions()` grouped raw broker positions with:
   ```ts
   const key = `${pos['underlying-symbol']}::${pos['expires-at']?.slice(0, 10) ?? 'unknown'}`;
   ```
   Symbol + expiration only. Two independently-opened spreads sharing both — differing only in strike and/or quantity — were merged into one `Position`, one card, one `creditReceived`.

2. **`creditReceived` on a merged group is a single aggregate dollar figure** (`calculateSpreadCredit`), summing every leg's entry economics with no per-spread breakdown retained.

3. **A systemic secondary defect compounded (1) and (2).** At least seven independent call sites needed a "per contract" number and each independently re-derived a stand-in "quantity" by picking a single arbitrary leg, then divided the AGGREGATE `creditReceived` by that one leg's quantity.

4. **Order construction itself was per-leg-correct; the defect was entirely upstream** in grouping and per-contract economics attribution.

## PRODUCT OWNER RULING (first round, REJECTED)

> The root-cause investigation is accepted. The implementation is rejected because grouping by quantity is not canonical position identity and leaves same-quantity independent spreads merged and live-submittable. Disclosure is not an acceptable substitute for a hard safety block.

The first round replaced the symbol+expiration key with a symbol+expiration+**quantity** key (`groupEconomicLegs`) and treated "every leg in a group shares one quantity" as sufficient proof that the group was one real position. It also introduced a `'block' | 'warn'` severity split, where a same-quantity ambiguous merge was **disclosed** in the confirmation modal (exact legs/strikes shown) but still **submittable**.

Both of these are withdrawn by this corrective round:

- **Quantity is not identity.** Two independently-opened spreads can share symbol, expiration, AND quantity (e.g. two separate 2-contract bull put spreads at different strikes opened on different days). A quantity-only key cannot tell them apart and would silently merge them exactly as the original symbol+expiration key did — it only narrows the collision space, it does not close it.
- **Disclosure does not mitigate a live financial action.** Showing the merged legs in a confirmation modal still allows the operator to click Confirm and submit a merged, economically-incoherent order. The original incident was caused by exactly a merged-and-submitted order; "you can see it's merged" does not change that outcome. Every rule in the corrected safety gate is now `severity: 'block'` — there is no warn-only path for a structural or economics defect.

## Corrected design

### Canonical module: `lib/portfolio/closeOrderSafety.ts`

Framework/React-free, independently unit-testable (45 tests, see Testing below). Exports:

- **`analyzePositionStructure(legs)`** — deterministic ECONOMIC-STRUCTURE ANALYSIS, replacing quantity-only grouping. For every symbol+expiration bucket, legs are bucketed by `(optionType, |quantity|)`; within each bucket, shorts and longs are paired: if one side is empty, every leg on the populated side is its own unambiguous `NAKED` structure (nothing to pair against); if exactly one short and one long exist, it is one unambiguous `VERTICAL`; any other combination where BOTH sides are populated (2 shorts + 2 longs, 2 shorts + 1 long, etc.) has more than one valid short↔long pairing and is returned as `status: 'AMBIGUOUS'` with full diagnostic detail on every ambiguous bucket. Same-quantity put-`VERTICAL` + call-`VERTICAL` pairs are merged into one `IRON_CONDOR` structure post-resolution — an iron condor is the same four legs as "one put spread + one call spread," not a competing partition choice, so this merge is itself unambiguous. **Strike adjacency is never used as a tiebreaker** — when a bucket is genuinely ambiguous, the module reports `AMBIGUOUS`, full stop, rather than guessing which pairing is "more likely" by strike proximity.

- **`buildCanonicalCloseIdentity(structure, key, underlying, expiration, contractMultiplier)`** — produces the one `CanonicalCloseIdentity` for an already-RESOLVED, unambiguous structure. Computes the TRUE SIGNED net entry economics (`netPerShare = Σ(short legs' avgOpenPrice) − Σ(long legs' avgOpenPrice)`) and classifies `entryPriceEffect: 'Credit' | 'Debit'` explicitly from the sign, instead of the pre-existing `calculateSpreadCredit`'s `Math.max(0, net)` (`app/portfolio/page.tsx:1938`), which silently floored a should-be-debit or corrupted-data net to exactly $0. This module **blocks** (`ENTRY_PRICE_EFFECT_INVALID`) rather than floors when net is exactly zero or non-finite, and **blocks** (`ENTRY_ECONOMICS_UNAVAILABLE`) when any leg is missing a valid entry price.

- **`computeBreakEvenClose(identity)`** — returns `{ pricePerUnit: identity.entryPricePerUnit, priceEffect: identity.entryPriceEffect === 'Credit' ? 'Debit' : 'Credit' }`. Explicitly mirrors the entry effect, so break-even realizes ~$0 for BOTH credit-opened AND debit-opened positions (the first round's implicit assumption that entries are always credits was never actually validated against a debit fixture).

- **`buildClosePlan(identity, requestedQuantity, closeableQuantity, closePricePerUnit, requestedClosePriceEffect)`** — the one IMMUTABLE plan object. Validates, in order: `REQUESTED_QTY_INVALID` (non-integer / ≤0 / non-finite), `REQUESTED_QTY_EXCEEDS_POSITION` (`0 < requestedQuantity ≤ closeableQuantity`), `LIMIT_PRICE_INVALID`, `LIMIT_TICK_INVALID`, `CLOSE_PRICE_EFFECT_INVALID`. Computes `legPayload` by scaling every leg's quantity to `requestedQuantity` (the canonical 1:1 leg ratio every currently-supported structure has — `submittedLegQuantity = requestedSpreadQuantity × canonicalLegRatio`, where `canonicalLegRatio` is always 1 today), then computes signed `closeTotalCashFlow` and `expectedRealizedPnl`.

- **`runCloseOrderSafetyGate(input)`** — typed validation gate with **19** stable `SafetyRuleId`s, **every one a hard block** (no `'warn'` severity exists anywhere in this module): `AMBIGUOUS_POSITION_STRUCTURE`, `ENTRY_ECONOMICS_UNAVAILABLE`, `ENTRY_PRICE_EFFECT_INVALID`, `CLOSE_PRICE_EFFECT_INVALID`, `CONTRACT_MULTIPLIER_INVALID`, `LEG_IDENTITY_MISMATCH`, `LEG_RATIO_MISMATCH`, `REQUESTED_QTY_INVALID`, `REQUESTED_QTY_EXCEEDS_POSITION`, `PAYLOAD_QUANTITY_MISMATCH`, `LIMIT_PRICE_INVALID`, `LIMIT_TICK_INVALID`, `QUOTE_MISSING`, `QUOTE_INVALID`, `QUOTE_CROSSED`, `QUOTE_STALE_UNCONFIRMED`, `BREAK_EVEN_PNL_MISMATCH`, `DISPLAY_PAYLOAD_ECONOMICS_MISMATCH`, `MATERIAL_PNL_DEVIATION`. A one-sided or crossed quote always blocks with no escape hatch; a stale-but-otherwise-valid quote blocks unless the caller explicitly passes `staleQuoteConfirmed: true` (an escape hatch reserved for that one condition — there is no silent or warning-only continuation for missing/invalid/crossed quote evidence). When `actualOrderLegs` (the real broker payload about to be submitted) or `displayedExpectedPnl` (what the UI shows) are supplied, the gate hard cross-checks them against the plan it just built, so the confirmation modal and the broker payload can never independently drift from each other.

- **`structureAnalysisToBlockingIssue(result)`** — converts an `AMBIGUOUS`/`UNSUPPORTED` structure-analysis result into a block-severity `AMBIGUOUS_POSITION_STRUCTURE` issue with full per-bucket diagnostic detail, used before a `CanonicalCloseIdentity` can even be attempted (there is no single structure to build one from).

### `lib/portfolio/closeOrderSubmission.ts` (new this round)

The minimum orchestration extracted from `app/portfolio/page.tsx` to make "a safety failure cannot reach a live broker submission function" a unit-testable property rather than an inline invariant verified only by inspection. It does not replicate order-body construction, GTC/OCO cancellation, roll input validation, or any React/UI state. Two guard functions:

- **`guardAgainstAmbiguousStructure({ identity, structureAmbiguous, structureBlockMessage })`** — the structure-level guard; must pass before a `SafetyGateInput` can even be constructed.
- **`guardWithSafetyGate(gateInput)`** — runs `runCloseOrderSafetyGate` and translates the result into an allow/block decision.
- **`submitCloseOrderIfSafe(structureGuardInput, gateInput, submitToBroker)`** — the single boundary every live submission passes through; `submitToBroker` is invoked if and only if both guards pass. Both real submission call sites (`BatchConfirmModal.submitAll`, `SetStopLossButton.submit`) delegate to these guards instead of duplicating the check inline.

### Ambiguous positions are hard-blocked everywhere, not just at final submission

Per the Product Owner's ruling that disclosure is not a substitute for a hard block, an ambiguous position is blocked at every layer, not only the broker call:

- `Position.identity: CanonicalCloseIdentity | null` and `Position.structureAmbiguous: boolean` / `Position.structureBlockMessage: string | null` are computed once in `loadPositions()` from `analyzePositionStructure` + `buildCanonicalCloseIdentity`, and are the ONLY source any live action may read quantity/economics from. `Position.quantity` is retained only for backward-compatible DISPLAY and is explicitly documented as non-authoritative.
- The position card's selection checkbox is disabled (and visually flagged with a red "AMBIGUOUS POSITION STRUCTURE — all actions disabled" banner) whenever `structureAmbiguous` is true, so an ambiguous position cannot even be added to a batch action.
- `SetStopLossButton` renders a disabled "BLOCKED" button (with the block reason as a tooltip) instead of its normal stop-loss control for an ambiguous position.
- `BatchConfirmModal.enrich()` produces an already-blocked `SafetyCheckResult` (`AMBIGUOUS_POSITION_STRUCTURE`) for any ambiguous item without attempting to build an identity or plan.
- `submitAll()` and `SetStopLossButton.submit()` both re-run `guardAgainstAmbiguousStructure` immediately before submission as defense in depth against state drift between enrich and submit, then re-run `guardWithSafetyGate` with the actual broker payload and displayed P/L for cross-check.

No residual ambiguity is disclosed-and-allowed anywhere in this design. Where the structure genuinely cannot be resolved (broker order/lot history that could disambiguate it is not fetched into this codebase's live position-loading path), the position is visible for awareness but every action is disabled until the operator resolves it manually (e.g. at the broker directly).

### Credit AND debit entry economics

The first round's `creditPerContract` naming implicitly assumed every entry was a credit. This round's `CanonicalCloseIdentity` carries `entryPriceEffect: 'Credit' | 'Debit'`, `entryPricePerUnit` (positive per-contract magnitude), and `entryTotalCashFlow` (signed, whole-position). `ClosePlan` carries the symmetric `requestedClosePriceEffect`, `closePricePerUnit`, `closeTotalCashFlow`, and `expectedRealizedPnl` (= prorated entry cash flow + close cash flow). Break-even for a debit-opened position now correctly computes as a Credit close at the same per-unit price, and both directions are asserted to realize ~$0 in tests.

## Broker convention evidence

Per the Product Owner's requirement that existing builders' correctness be demonstrated with exact code references, not merely asserted:

- **Price sign convention (`app/portfolio/page.tsx:1869-1894`, `buildCloseOrder`).** TastyTrade's `price` field is always a positive magnitude; direction is carried separately by `'price-effect': 'Debit' | 'Credit'`. `buildCloseOrder` computes `priceEffect = limitPrice < 0 ? 'Credit' : 'Debit'` and submits `Math.max(Math.abs(limitPrice), 0.01)` as `price` — this is why `ClosePlan.closePricePerUnit` is likewise always a positive magnitude with the sign carried by the separate `requestedClosePriceEffect` field, matching the broker's own convention exactly rather than translating between conventions at the submission boundary.
- **Opening credit convention (`app/portfolio/page.tsx:1896-1920`, `buildOpenSpreadOrder`).** Submits `'price-effect': 'Credit'` unconditionally with `price: Math.max(Math.abs(credit), 0.01)` — opening a new spread in this app is always modeled as a credit order (short leg `Sell to Open`, long leg `Buy to Open`), which is why the Roll workflow's new-spread economics (`finalCredit`, validated by the existing 1/3-of-width credit rule at `app/portfolio/page.tsx:4771-4773`) are handled entirely separately from the CLOSING leg's `CanonicalCloseIdentity`/`ClosePlan` — they are two different orders with two different, independently-validated economics, never merged into one identity object.
- **The ×100 contract multiplier (`app/portfolio/page.tsx:1930-1939`, `calculateSpreadCredit`).** `avgOpenPrice` is a per-share option price; `calculateSpreadCredit` computes `net = Σ(±price × qty)` (still per-share) then returns `Math.round(net * 100 * 100) / 100` — the first `* 100` is the contract multiplier converting per-share dollars to per-contract dollars, the second `* 100 … / 100` rounds to the nearest cent. This is the exact defect location: `Math.max(0, …)` is absent from this quoted line in the corrected module (this repository's `calculateSpreadCredit` still contains it and remains unused by any of the corrected call sites; `buildCanonicalCloseIdentity` in `lib/portfolio/closeOrderSafety.ts` reimplements the multiplier without the floor). The corrected module applies the identical `× contractMultiplier` (parameterized, always 100 for equity/index options in this app) but never floors the signed result.
- **Roll's net economics vs. close-only realized P/L (`app/portfolio/page.tsx:4826-4868`).** A roll is submitted as one atomic `type: 'OTOCO'` complex order: `'trigger-order': item.orderBody` (the CLOSE order, built from and safety-gated against the position's own `CanonicalCloseIdentity`/`ClosePlan`, exactly like a standalone close) with `orders: [openBody]` (the NEW spread, built by `buildOpenSpreadOrder` from the roll's own `finalCredit`). If the trigger (close) fills but the contingent (open) never fills, the position ends up flat, never half-rolled naked — there is no state where the close's realized P/L and the new position's opening economics are combined into one number anywhere in this design; they remain two separate orders with two separate, independently-computed economics for exactly as long as the OTOCO is pending, and remain two separate positions (one closed, one newly opened) once both legs fill.
